# Simpl Courses for iOS

The iOS app is the extension in a different wrapper: the student's own Canvas site in a web view, with the same scripts and stylesheet injected into every Canvas page — and, since 2.99 (the iPhone app's 1.0), Apple's own app on top of it: the tab bar, the navigation bars, the search field, the sheets and menus, the haptics and the root screens are native (Liquid Glass on iOS 26), and the web view sits underneath as the engine that reads Canvas for them. Signing in happens on the school's real sign-in page inside the app, so the app needs no API key or developer key from the school; it keeps a password only when the student asks it to (*Stay logged in?*, below), in the Keychain of that one iPhone.

## How it works

```
ios/
  project.yml                     XcodeGen spec → SimplCourses.xcodeproj (also committed, kept in step by hand)
  SimplCourses/
    App/                          SwiftUI: school picker, the settings sheet, the app session
    Native/Engine.swift           the web view as the engine: calls into the page, the one web view moved between screens
    Native/Shell.swift            the root (engine underneath, native chrome over it), the tab bar, the account menu, What's New
    Native/WebScreen.swift        a screen of the web interface pushed on a native stack
    Native/TodayView.swift …      the native screens: Today, Courses, To Do, Grades, Calendar, Notifications, Search
    Native/ContextHome.swift      a course's home (or a group's): its grade ring, section tiles, work, announcements
    Native/CourseSections.swift   a course's sections: announcements, discussions, assignments, modules, pages, files, people, quizzes, syllabus
    Native/TopicView.swift        an announcement or a discussion with its threaded replies, and Reply
    Native/AssignmentView.swift   an assignment, its grade, the rubric sheet, comments, Hand In at the bottom (no tab bar) and its half sheet
    Native/QuizView.swift …       a quiz in the app's own screen (QuizRun.swift: the attempt; QuizModels.swift: its answers)
    Native/ToolSheet.swift        an external tool in a full-height sheet, through Canvas's sessionless launch
    Native/SetupView.swift        the iPhone's own guided setup: the courses that count and the goals
    Native/TabBarProbe.swift      the tab bar's glass measured (its size, for screens that draw over it)
    Native/InboxView.swift        Groups, the Inbox, a conversation, New Message
    Native/Router.swift           which Canvas addresses open a native screen; links in rich text
    Native/RichText.swift         Canvas's own HTML (instructions, a post, a page) in a small self-sizing web view
    Native/Components.swift       the grade ring, status chips, avatars, rows, the screens' loader
    Native/Models.swift …         what the page answers, decoded (CourseModels.swift: a course's, a group's, the Inbox's)
    Native/Style.swift            haptics, Liquid Glass (with a material before iOS 26), chips and badges
    App/LoginOverlay.swift        the sign-in form, "Logging you in" and "Stay logged in?" over the web view
    Web/WebController.swift       one WKWebView with the extension injected + navigation/dialog delegates
    Web/login.js                  the sign-in reader (its own content world, on every page): what a page asks for
    Web/LoginAssist.swift         decides what covers the page and when details go in; the Keychain vault
    Web/FilePreview.swift         a file fetched with the web view's session, shown in Quick Look in a sheet
    Web/ScriptBundle.swift        reads the bundled extension/manifest.json and builds the WKUserScripts
    Web/bridge.js                 stands in for the browser-extension APIs inside the page
    Web/Bridge.swift              the native half: storage, sign out, settings, alerts, action sheets, files, swipe-back
    Web/BridgeStore.swift         storage.local as one JSON file in Application Support
    Resources/Assets.xcassets     the app icon (rendered by scripts/make-icons.mjs)
```

- **The extension ships unchanged.** The `extension/` folder is a folder reference in the Xcode target, so the app bundle carries the same files the Safari and Chrome builds do. `ScriptBundle` reads `manifest.json` and injects each `content_scripts` entry at its `run_at`, into an isolated content world (like an extension's content scripts), main frame only, and only on the configured Canvas host. That includes the group the browsers never match (`https://lazy.simplcourses.invalid/*`; the Chrome builds leave that group out, since Chrome would list its host as a site the extension reads, and load the same files from `content/app/lazy-modules.js`, the list the group mirrors): in a browser those files — the quiz flow, the hand-in block, the tools' bodies, the setup, the phone layout — are loaded on demand through the background (`content/app/lazy.js`); the app has no scripting API, so it puts them all in at once, and the loader finds them already there. Single sign-on pages on other hosts are left untouched.
- **`browser.*` is a bridge.** `bridge.js` is injected first and provides `storage.local` (+ `onChanged`), `runtime.sendMessage`/`onMessage`, `runtime.connect`/`onConnect`, `getManifest`, `openOptionsPage`, and inert `action`/`permissions`/`tabs`. `background.js` runs inside the same page, so the message ports and the settings page work exactly as in the extension. Storage lives in a native JSON file shared by every web view the app opens; a change in the settings sheet reaches the Canvas view through `storage.onChanged`.
- **Apple's own chrome, the page underneath (2.99).** Once a signed-in Canvas page with the interface on is up, the page says so (`shell.state`, from `extension/content/app/native-app.js`, which only the app injects — it sits in the on-demand group) and the app puts its own interface over it: a SwiftUI `TabView` with **Today, Courses, To Do, Grades** and a **Search** tab (iOS 26 draws it in Liquid Glass and shrinks it as a list scrolls; five is the most a phone's tab bar shows before it folds the rest into *More*, so since 1.1 the **Calendar** is pushed from the calendar button on To Do, and a link to the calendar in a page opens it over To Do), a `NavigationStack` per tab, and native screens — lists, swipe actions, context menus, sheets with detents, a grade ring per course, a Swift Charts trend, native date pickers, alerts with text fields, `.refreshable`, the search field — every number in them asked of the page (`BCVNative.call('today')`, `'courses'`, `'todo'`, `'grades'`, `'calendar'`, `'notifications'`, `'search'`, and the actions: tick, priority, add or delete a task, nickname, goal, target, calendars, read/clear) and worked out by the same store and rules the web screens use, so nothing is counted twice or differently. **Since 1.2 a course is native too**: a press on a course, or any Canvas address the app is handed (a row, a notification, a link in a post), goes through `Router.swift`, and a course and everything in it — its home (the grade ring, a tile per section, the work still to do, the latest announcements, the front page, the course's own links), announcements, discussions and a discussion with its replies threaded and **Reply**, assignments and an assignment (instructions, your work, the grade with the class's numbers, the rubric, comments and **Add a Comment**, and **Hand In**: text, a web address or files from Files or Photos, as the assignment takes them), modules with **Mark done**, pages, files (folders pushed, a file in Quick Look), people (a swipe to message one), quizzes, the syllabus and the course's grades — a group and its sections, **Groups**, and the **Inbox** (mailboxes, a conversation as bubbles with a reply bar, **New Message** with people found as you type) are SwiftUI screens fed by more calls (`home`, `announcements`, `discussions`, `topic`, `reply`, `modules`, `markDone`, `assignments`, `assignment`, `submit`, `commentOn`, `pages`, `page`, `files`, `people`, `quizzes`, `syllabus`, `courseGrades`, `groups`, `inbox`, `conversation`, `sendReply`, `star`, `recipients`, `composeContexts`, `sendMessage`); Canvas's rich text (instructions, a post, a page) is the HTML the page cleaned, in a small web view that sizes itself (`RichText.swift`). On **Grades** each course is a set of **rings within rings** drawn by the app — the total outermost, then a ring per assignment group with graded work, each in its colour — that fill once; a press opens that course's grades in a sheet, the only place its item grades are listed (by group, or sorted by grade, due date or name), with a **What-If Scores** switch: with it on, every score is a field to type into, **Add What-If Assignment** puts a made-up assignment in a group, and the total, the letter, the rings and the term GPA follow (nothing is saved; a swipe puts a real score back). **Since 1.3** a **quiz** is taken in the app's own screen over everything (`QuizView.swift`, from the page's `quizIntro`, `quizBegin`, `quizAttempt`, `quizAnswer`, `quizFlag`, `quizUpload`, `quizGo`, `quizSubmit` and `quizFeedback`, which share the web quiz screen's rules, `BCV.screens.quiz.logic`): the intro with its rules and the access code, one question at a time with a numbered strip, flags and the clock, every Classic kind (multiple choice, true/false, multiple answers, short answer, number and formula, essay, matching, dropdowns, fill in the blanks, file upload, text only), a quiz set to one question at a time read through Canvas's own take page, the review, the receipt and the feedback; an **external tool** (an assignment's, a New Quizzes quiz, a module item, a course's own) opens in a full-height sheet through Canvas's sessionless launch (`toolLaunch`), with back, reload and Safari; an assignment's **Hand In** bar is exactly the tab bar's width and height (measured, `TabBarProbe.swift`), its sheet opens half-height, and the **rubric** opens in a sheet from a button by the grade. **Haptics** on every tick (success), every switch, segmented control and tab (selection), every swipe action and sheet put away (rigid, soft), every error; the web screens ask for the same (`BCVBridge.native.haptic`). Anything the app does not draw — Canvas's own page for something (*Open Canvas's Page*, *Canvas's Quiz Page*), the profile — is the web interface, **pushed on the native stack** (`WebScreen`): Apple's navigation bar over it with the screen's title (the page says it: `shell.page`) and Back, the edge swipe the stack's own, the page under the bars (their heights reach the stylesheet as `--bcv-shell-top` / `--bcv-shell-bottom`, and the page draws neither of its own bars: `html.bcv-native-shell`). There is one web view: it moves into the web screen showing (the screen it leaves keeps a picture of itself for the push, the pop or the tab switch) and is asked to draw that address (`BCVNative.show`, in place where the interface draws it); a press in it that would move the page asks the app for a new screen instead (`shell.open`; a link to a root screen switches the tab, `shell.tab`); a quiz attempt puts the bars away (`shell.focus`). While no web screen shows it the web view waits underneath, covered. **Signing in and the interface switched off** keep the web view whole, as before (the chrome comes on when the page says so). Each tab's large title sits on the bar's row, at the leading edge, with the screen's buttons and the picture in one glass capsule at the other end (Today: the bell; To Do: grouping, the Calendar and a new task). The account menu under the picture holds Inbox, Groups, the appearance, Settings, What's New (a native sheet, also shown once after an update) and Sign out. The defaults key `nativeShellOff` turns the native chrome off (the page then draws its own, below).
- **Without the native chrome** (sign-in, setup, `nativeShellOff`) the web view fills the screen, under the status bar and the home indicator, and the interface draws its own bars: the phone layout's tab bar and back bar (below). `ScriptBundle` sets `viewport-fit=cover` on every Canvas page so the stylesheet can read the safe-area insets, and the web view's own inset adjustment is off so nothing is padded twice. Pull down to reload. The settings sheet (opened from the account sheet's Settings row) shows the school, the version, and the extension's own `options.html` loaded from the bundle (its "Canvas sites" section is hidden: the school is chosen natively). JavaScript alerts and confirms (leaving a quiz, submitting) become native alerts; `window.open` to another host opens an in-app Safari sheet. **Nothing zooms:** the viewport is fixed at the device width (`maximum-scale=1, user-scalable=no`, so focusing a field does not zoom either) and every page and frame gets `touch-action: manipulation`, so a double tap is two taps, never a zoom.
- **The phone layout.** `extension/content/app/phone.js` and the phone block of `app.css` rebuild the screens for a narrow touch screen when the viewport is 700px or less (decided before first paint, so the same files serve a phone-sized browser window too): a five-item tab bar (Today, Courses, To Do, Grades, Calendar) and a back bar on every pushed screen, both true glass (a low-opacity tint over `blur(30px) saturate(1.9)`, a hairline, an inset specular, a solid fallback where blur is unavailable) that the content scrolls under; an edge-swipe from the left pops the stack like the Back button (not during a quiz); in the app that swipe is the phone's own (WebKit's back gesture, which follows the finger), switched on by the page only where there is somewhere to go back to — not on a tab's root, not during a quiz, not under a sheet — and the page's own swipe stands down, so one swipe is one Back. Back goes back through the history (each in-page move is counted in `history.state.d`), never piles a new entry on. A course's screens carry its section chips at the top, Home included, the one you are on lit and scrolled into view. Large titles, grouped inset lists, screens that push in at .3s with rows staggered 70ms (capped at 280ms). **Swipe a row left** for its actions — Done / Priority on a To Do task, Read / Clear on a notification, Nickname on a course — up to 152px, latching past half, one row open at a time; every swipe action is also a tap target. Anything modal is a **bottom sheet with a grab handle**, held like the phone's own: drag it by the handle, its head, or a list already at its top — up, and a sheet holding more than it shows grows to nearly the full screen; down, and it comes back to its own height, or goes (a far or fast pull) as its own Cancel would; a list scrolled down scrolls back first. Every sheet gets a grabber, prompts and questions included. A short question (*Delete this task?*) is the phone's own alert, and a menu or a picker its own action sheet (`BCVBridge.native.ask` / `.menu`). A To Do row opens a task sheet (priority, mark done, open the assignment, delete a task of your own); a **grade ring expands on a tap** (one course at a time) into the category rings, a per-group breakdown and the target picker, and a what-if switch tries scores without saving anything; an assignment is handed in on its own page, the submit block at the end of the same scroll; a quiz attempt takes the whole screen. The bell on Today opens Notifications; Inbox, Groups, the appearance switch, Settings and Sign out live under the avatar. **Only the courses chosen in setup appear**, on every surface and in every count — the list is filtered before anything is counted (new enrollments are visible until the selection is changed in Settings). There is **no Immersive Reader on the phone**: iOS has Reader, Speak Screen and Dynamic Type.
- **What only the app can do** is exposed as `BCVBridge.native` (null in a browser): `signOut()` clears the Canvas session's cookies and site data (and the saved sign-in) and reloads to the login page; `ask()` and `menu()` are the phone's own alert and action sheet; `previewFile()` opens a file in the phone's own viewer; `navState()` turns the phone's swipe-back on or off for the screen showing.
- **Files open in the phone's own viewer.** A file the interface opens, or a link the web view cannot show as a page, is fetched with the web view's own session (`WKDownload`: its cookies, its redirects to the school's file host) into a temporary folder and shown in Quick Look in a sheet — pinch, page, share and mark up as with any file on the phone; drag it down to put it away, and the copy is deleted.
- **Saved sign-in.** The school picker asks for the school's Canvas portal link. `Web/login.js` runs in a content world of its own on every page (the page's scripts cannot see it or hear it) and says what the page asks for: a username and password, a username alone (the first step of a two-step sign-in), a password alone, or nothing (a code page, two-factor, a consent page). When it finds a sign-in form, the app covers the page with its own form (*Sign in to your school*, the host it goes to shown under it); what is typed goes into the page's own fields and its own button is pressed. Once Canvas is reached it asks **Stay logged in?**; yes keeps the username and password in the Keychain (this device only, readable only while it is unlocked, never synced or backed up), for that one sign-in page only. From then on, when that page comes up, **Logging you in** covers it from the first frame (a ring going round), the details are filled and sent, and a two-step page gets the username and then the password. A two-factor prompt is shown, uncovered, to be finished by hand, with a note over it (*Finish signing in below*; 1.4); and after a moment under *Logging you in* a **Show the Page** button lifts the cover for anything else the school's page wants done by hand — the sign-in carries on once Canvas is reached. A wrong password brings the form back saying so, and saved details that failed are not tried again until new ones are given. *Use the website instead* leaves the page as it is. Settings shows the saved sign-in and forgets it; signing out forgets it too. Light or dark is the phone's own setting (1.4): the app pins neither, the saved appearance is held at "system" (`Bridge.followingPhone`, on every settings write and at launch), and the settings page shows no Light/Dark/System choice in the app.
- **The first launch opens the iPhone's own guided setup** (1.3, `SetupView.swift`), after Canvas's own sign-in, over Today: a welcome, the courses that count (ticked, with a nickname each), the grade history and GPA goal, a target per course (or Pass/Fail), and a read-back — nothing of the look, the colour or the layouts, which the app draws itself. It writes the same answers the web setup does (`setupInfo`, `setupSave`), and the page's web setup stands down while the app's chrome is on. It can be run again from **Settings → Courses and Goals**. Without the native chrome (`nativeShellOff`) the first launch opens the web setup (`/?bcv=setup`) as before. The settings page's own "Guided setup" section is hidden in the app, like "Canvas sites".
- **The session survives a relaunch.** WebKit keeps cookies without an expiry date (Canvas's session cookie is one) in memory only, so an app that was closed came back at the login page. `CookieJar` mirrors the web view's cookies into the Keychain whenever they change and when the app leaves the foreground, and puts them back before the first load. On Canvas's own login form "Stay signed in" starts checked (it can be unticked). Sign out empties the jar.
- **Canvas's bundles load only where Canvas draws the page.** `ContentRules` compiles two content-rule lists: telemetry (New Relic, Pendo, analytics), blocked everywhere; and Canvas's script and stylesheet bundles, blocked only on pages the interface draws itself (`RenderedRoutes`, a port of `parseRoute` and the course and group tab switches). Those pages no longer download, parse and run Canvas's front end to build a page that stays hidden, which is most of the time a tap used to take. Pages handed back to Canvas (a quiz being taken, a file preview, an external tool, `?bcv=native`, everything when the interface is off) and frames (tools) are untouched; switching the interface on or off reloads the page so the right rules apply.

## Versions

The iPhone app has its own version line: **1.0** (build 1) was the first with the native chrome, shipped with the interface's 2.99; **1.1** (build 2, with 2.99.1) moved the Calendar off the tab bar and drew the counters and filter chips as solid cards (Liquid Glass stays on the bars and controls, as in Apple's apps); **1.2** (build 3, with 2.99.2) drew a course and everything in it, Groups and the Inbox natively, with Hand In, Reply and New Message, gave Grades its rings and a what-if sheet per course, and leaves Simpl's Tools out of the app for now; **1.3** (build 4, with 2.99.3) takes quizzes in the app's own screen, opens external tools in a sheet, adds its own guided setup, nests the grade rings with a What-If switch and what-if assignments, and sizes the Hand In bar to the tab bar; **1.4** (build 5, with 2.99.5) follows the phone's light or dark, turns formula pictures light in dark mode, reads formulas as maths on the quiz review, offers *Show the Page* while signing in, puts each screen's main action at the very bottom in place of the tab bar (`ActionButton`: Liquid Glass concentric with the phone's corners), lets a swipe right on a piece of work hand it in or open its feedback, opens Today's counter sheets halfway first, and takes a quiz a question at a time by pulling up (a pick moves on by itself; pull up and hold on the last question hands it in); each release that changes the app raises it (1.1, 1.2 …; the build number counts up with every upload). `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` in `ios/project.yml` (and the committed project, kept in step: the smoke suite checks) feed `CFBundleShortVersionString` and `CFBundleVersion`. The interface inside it keeps the extension's number (`extension/manifest.json`); Settings shows both.

## Build and run

1. Xcode 26 or later (the iOS 26 SDK: the bars are Liquid Glass and the shell uses its APIs; the app runs on iOS 18 and later), and Homebrew (for XcodeGen; the script installs it).
2. Generate and open the project:
   ```bash
   ./scripts/build-ios-app.sh --open
   ```
3. In Xcode select the **SimplCourses** target → Signing & Capabilities → choose your Team (a personal Apple ID team is enough to run on your own iPhone).
4. Pick your iPhone or a simulator and press ⌘R.
5. In the app enter your school's Canvas address (for example `school.instructure.com`), sign in on Canvas's page, and the interface takes over.

`.github/workflows/ios.yml` compiles the app for the simulator on every push that touches `ios/` (no signing, Xcode 26 on `macos-26`), so a Swift error shows up without a Mac at hand. `.github/workflows/ios-shots.yml` goes further: it runs the app on an iPhone 17 Pro simulator against the mock Canvas (`-SimplBaseURL http://localhost:8800`, storage seeded as a student who has used it with `-SimplDemo YES`, a tab, a sheet or a pushed screen chosen with `-SimplTab`, `-SimplSheet`, `-SimplPush`, and `-SimplOpen grades:<course>`, `handin`, `quiz:<course>:<quiz>[:take:<question>]`, `tool:<course>:<tool>` or `setup` for the grades and Hand In sheets, a quiz, a tool and the setup), pictures every native screen in light and dark (`scripts/dev/ios-shots.sh`) and pushes the pictures and the build log to the `ios-shots` branch. `scripts/dev/ios-test.mjs` checks the app's side of the page in Chromium with a stand-in for the native bridge: with the native chrome, every engine call the native screens make (their shapes and their actions: a tick, a priority, a read mark, a reply, a hand-in, a what-if score, a message, a quiz begun, answered in every kind, flagged, handed in and its feedback read, the setup written and read back) and no Tools in the app and the navigation hand-offs (`shell.state`, `shell.page`, `shell.open`, `shell.tab`, a screen shown in place without a history entry); without it, the viewport and no zoom, course navigation and the swipe-back state, the native alert, action sheet, picker and file viewer, sheet gestures by touch, and the sign-in reader on stand-in school pages (a full form, two steps, a new-password form, a code page, an error). `scripts/dev/hybrid-test.mjs` checks the injection model without an iPhone: it injects the bundle into the mock Canvas in headless Chromium the way `ScriptBundle` does and exercises the bridge (storage and `onChanged`, the message bus, the host guard). `scripts/dev/phone-test.mjs` walks the phone layout at an iPhone viewport (the five tabs, the sheets, a course, an item, submit, a quiz, the tools) and saves screenshots to `scripts/dev/out/phone-*.png`.

## Known limits

- **Single sign-on inside a web view.** Shibboleth, SAML and Microsoft logins work. Google sign-in refuses embedded web views by policy, so a school on Google Workspace cannot sign in this way. A sign-in page the reader cannot read (a form drawn in a frame, an unusual field) is simply shown, as before.
- **Canvas-drawn pages** (a page the interface hands back to Canvas) are Canvas's own responsive layout under the interface's bars; an external tool is the tool's own page in its sheet.
- **Not in the app yet:** Simpl's Tools (citations, the focus timer, flashcards and the rest — no Tools row, page or command); handing in a media recording or an annotation (the Hand In sheet says to use Canvas's own page); files over 50 MB from the phone, for a hand-in or a quiz's file question; the web quiz screen's developer *Import answers*.
- **Files** open in Quick Look (its share button saves one to Files); **the app icon badge** is not set (the extension's toolbar badge has no equivalent yet).
- **App Store review** will ask why the app displays a third-party service: it re-renders the student's own Canvas from Canvas's public API and needs a demo login (a Canvas Free-for-Teacher account works).
